# Phase 4 plan — Judgment collection and retrieval

Status (2026-10-20): **engineering implemented** — schema, importer, search,
Research tab, Precedent Library and evaluation machinery, tested with
SYNTHETIC data (`docs/PHASE4_EXECUTION_LOG.md`, ADR 0018). **External inputs
still pending:** an approved judgment source (so the live collection is
empty) and a lawyer-labelled evaluation set. The plan below is kept as
written; this document contains no judgments, citations, source URLs or
claims about any source's terms of use.

## Scope (from `docs/DEVELOPMENT_BRIEF.md`, Phase 4)

- Ingest a curated set of judgments with metadata: title, citation, court,
  year, bench, practice area, source URL, full text.
- Hybrid search: PostgreSQL full-text (keyword) plus vector similarity, merged
  and ranked.
- Connect the Research tab to real search: citation, court, year, a relevant
  passage, and a link to the full text.
- A Precedent Library page for browsing the collection.
- An evaluation set: for 10–20 sample cases, the judgments a lawyer considers
  relevant; measure recall@10 and precision@10.

Done when: search returns only judgments in the collection; evaluation numbers
are recorded in the repository; nothing is generated by an LLM.

## What can be built once a source is approved

Proposed milestones (each with tests, a log entry and a local commit, as in
Phase 3):

1. **P4-M1 Schema.** `judgments` (title, neutral or reported citation, court,
   decision date and year, bench, practice areas, source name, source URL,
   terms-of-use record: the terms' URL, version or date, who checked them and
   when, and what they permit), with `judgment_sections` and `judgment_chunks`
   reusing Phase 3's page-aware chunking. Nothing is inserted by the migration.
2. **P4-M2 Ingestion command.** `python -m lexflow.cli.judgments import
   <folder>` reads files the owner placed locally plus a manifest (CSV or
   JSON) with the metadata above. It refuses entries without a source URL and
   a terms-of-use record, de-duplicates by citation and SHA-256, extracts text
   with the Phase 3 extractors and worker, and audits each import. **No
   crawling or downloading** by LexFlow; files come from the owner.
3. **P4-M3 Keyword search.** PostgreSQL full-text search (`tsvector` over
   chunks, `websearch_to_tsquery`, English configuration), with passages
   returned as stored chunk text and page numbers.
4. **P4-M4 Vector search and merge** (needs pgvector and the local model).
   Embeddings for judgment chunks with the same model as case chunks;
   reciprocal-rank fusion of keyword and vector results; every result is a
   stored judgment.
5. **P4-M5 Research tab and Precedent Library.** Real results only (citation,
   court, year, passage, link to the full text in LexFlow and to the source
   URL); an honest empty state while the collection is empty.
6. **P4-M6 Evaluation.** `evaluation/` with the lawyer's relevance lists (case
   ids to judgment ids), a script computing recall@10 and precision@10, and the
   recorded results. Re-run after any retrieval change.

## Decisions for the owner

1. Approve `pgvector/pgvector:pg17-trixie` (or another image) for development
   and CI, so vector storage can proceed under the database safety procedure.
2. Choose the source(s) and record their terms of use; confirm the practice
   areas and the size of the first set.
3. Arrange the relevance judgments with a lawyer for the evaluation set.
4. Confirm the local embedding model (`BAAI/bge-small-en-v1.5`, English) or a
   multilingual one if judgments in Hindi or other languages are expected.
